# labelcast-lab

**Occlusion-aware 3D label placement for three.js scenes: on the bundled 40-label scene the
placer removes every screen-space box overlap — 10 overlapping pairs → 0 (baseline
`baseline/naive.mjs`, which is what "draw a div at the projected anchor" gives you) — while
every label also carries a `visible / occluded / behind` verdict with the **blocking triangle
as a witness**, reproduced 40/40 by an independent oracle. 1.936 ms median per full placement
(302 triangles × 40 labels, 12,080 ray-triangle tests). On crowded 6-label views the placement is
**up to 25.0 % above the exhaustive optimum** (`bench/oracle.mjs`, 531,441 combinations) — the
greedy+local search is a fast feasible heuristic, *not* an optimal one, and the README says so.**

Upstream: none

This is an original tool (no fork, no vendored code). The 3D scene is generated by
`tools/gen-sample.mjs` from a fixed seed — nothing large is committed.

## What it does

Given a triangle mesh, a set of world-space anchor points and a perspective camera, `src/core.mjs`
returns for every label:

1. **Visibility** — `visible`, `occluded` (plus the index of the nearest blocking triangle and the
   hit distance along the anchor→eye segment), or `behind` (the anchor is at/behind the eye plane).
2. **A placement** — a screen-space box position and a leader line, chosen from a discrete candidate
   set (the anchor itself, plus 8 compass directions at each ring radius) so that no two boxes overlap.
   Greedy in priority order (visible anchors first, occluded ones after), then local search; both are
   deterministic.
3. **An audit** — `auditPlacement()` re-counts overlaps, leader length, occluded ids and the witness
   triangles straight off the returned items, so a third party never has to trust `stats`.

## Run it

```bash
node tools/gen-sample.mjs      # writes data/scene.json + data/reference.json (deterministic)
node bench/verify.mjs          # 13 behavioural assertions, exit 0 = all hold
node bench/bench.mjs           # warmup 1 + 7 timed runs -> bench/result.json
python3 -m http.server 4173    # then open http://localhost:4173/  (three.js 0.169.0 via importmap)
```

Node >= 20 is required (this repo was tested on v24.19.0). No `npm install`, no bundler, no
`node_modules/`: the page pulls `three@0.169.0` from jsDelivr with a pinned importmap, and all
geometry/visibility/placement maths runs in `src/core.mjs`, the *same file* node runs.

## Evidence (all of it from real runs; see `bench/result.json`)

| claim | measured | how to reproduce |
| --- | --- | --- |
| overlapping pairs, baseline → placer | **10 → 0** | `node bench/verify.mjs` (A4a/A4b) |
| visibility vs independent oracle | **40/40 status, 26/26 witness triangles** | A3 |
| projection vs independent projection | max **1.7e-13 px** | A2 |
| witness hit distance vs oracle | max relative **4.2e-16** | A10 |
| optimality gap vs exhaustive optimum (n=6, 9 candidates, 531,441 combos) | **0 % on a roomy view (vacuous: both sides cost 0), 25.0 % worst case on a crowded 320×200 view** | A6a/A6b |
| scale invariance, s ∈ {1e-6, 1e-3, 1, 1e3, 1e6} | **0 status mismatches / 200 checks**, screen drift **1.7e-13 px**, zero overlap at 5/5 scales | A7 |
| determinism | identical `items` hash over two runs and two generator runs | A1/A9 |
| timing | median **1.936 ms** (min 1.164 / p95 4.726 / cold start 14.307), RSD **44.2 %** | `node bench/bench.mjs` |

`rsdPct = 44.2 %` is far above 10 % and is reported as-is: the workload is ~2 ms, so on this shared
4-core box the run-to-run spread is dominated by GC and scheduler jitter, not by the algorithm.
`min` and `p95` are published next to the median for that reason. **The timing row above is quoted
verbatim from the committed `bench/result.json`; re-running `bench.mjs` overwrites that file with a
new run and the absolute milliseconds will move (observed range across runs: median 1.77–3.51 ms),
while the ratio-based claims (10 → 0 overlaps, 40/40 oracle agreement) stayed identical.** The cold
start (14.3 ms) is the first `placeLabels` call in a process and includes JIT warm-up; it is not
used anywhere as a claim.

## 本轮创新

**首次把「标签可见性见证」和「零重叠屏幕布局」放进同一条可独立复算的管线**：不是再写一个
CSS2DRenderer 式的“把 div 钉在投影点上”，而是给出三态判定 + 遮挡三角形见证（A3/A10 由独立
oracle 复核），再在该判定之上做离散候选的零重叠布局（A4/A6）。three.js 的 `CSS2DRenderer` 既不
做碰撞规避也不做遮挡测试；GIS 的 label declutter（如 Cesium `LabelCollection`）做屏幕空间去重，
但不返回遮挡见证、也不给出可复算的审计对象。本仓的设计目标是**同一份 `src/core.mjs` 同时被 node 与页面引用**，页面把
overlaps / visible / occluded 与 node 烘焙的 `data/reference.json` 逐项比对（HUD 里的
"vs node bake" 一行）。**但本轮无头环境没有真正执行过页面 JS**（只验了 200 + importmap +
`main.js` 静态检查），所以这是**接线**，不是已跑的浏览器证据——见 Known limits 最后一条。

**诚实边界（独立 prior-art 复核后的定档理由，2026-11-13）**：屏幕空间的点要素标注去重是 1990 年代
就成熟的教科书问题（Christensen/Marks/Shieber 1995, *ACM TOG*, DOI 10.1145/212332.212334；
Edmondson et al. 1996, *Cartographica*, DOI 10.3138/u3n2-6363-130n-h870），射线求交与"最近遮挡面"
也是标准 raycast（three.js `Raycaster` 本来就返回 `faceIndex`）。所以本仓**不主张新算法**；可辩护的
新意是**把三件事装进同一条可复算管线**：(a) 三态可见性 + 遮挡三角形见证、(b) 离散候选的零重叠布局、
(c) 不依赖 `stats` 的独立审计对象，并让同一份 core 在 node 与浏览器两端互相对账。只读 prior-art
检查覆盖 three.js CSS2DRenderer/CSS3DRenderer v0.187.0 源码、deck.gl `CollisionFilterExtension`、
Cesium `LabelCollection`、`labelgun`、`d3-labeler`、Mapbox GL symbol layers：**没有任何一个同时覆盖
(a)(b)(c)**，也没有任何一个把遮挡三角形作为标注溯源输出。定档 **B（下限）**，差异点是审计/溯源层，
不是布局搜索本身。

## Known limits (read this before trusting a number)

- **Absolute constants are disclosed.** `TOL_RAY = 1e-9` (hit window, as a fraction of the
  anchor→eye distance) and `TOL_DET = 1e-12` (parallel test, scaled by `|e1|·|e2|`) are both
  **relative**, so the pipeline is scale invariant over at least 1e-6 … 1e6 world units (A7).
  The oracle deliberately uses **different** constants (`TOL_BARY = 1e-9` on dimensionless
  barycentric coordinates, `TOL_T = 1e-7` on the segment parameter) so that "oracle agrees" is
  not an artefact of a shared magic number. Below ~1e-7 world units a triangle's area underflows
  and hits are no longer reliable — do not use this at that scale.
- **The oracle shares the candidate generator, not the search.** A6a/A6b compare our greedy+local
  search against exhaustive enumeration over the *same* discrete candidate space
  (`candidateOffsets`). If a good placement exists outside that candidate set, neither method finds it.
- **The placer is NOT optimal, and this is measured.** A6a (default viewport) reports 0 vs 0 and is
  therefore **vacuous** — it proves feasibility, not optimality. A6b forces crowding at 320×200 and
  finds a real worst-case gap of **25.0 %** in leader length (216.0 px vs the exhaustive 172.8 px),
  with both sides still at 0 overlaps. A pairwise-swap local-search pass was tried locally and
  discarded (it did not reduce the gap and was much slower); it is **not** in the committed history,
  so treat that as a note, not as evidence — the only placement evidence in this repo is A4/A5/A6.
- **The optimality claim is only for n = 6.** Exhaustive enumeration is 9^6; for the full 40-label
  scene the placer's result is *feasible* (0 overlaps) but has no optimality proof.
- **Occlusion uses the anchor, not the label box.** A label whose anchor is visible may still have
  its box drawn over a part of the mesh; occlusion is a property of the anchor point and is reported
  with its witness so you can decide what to do about it.
- **Occlusion priority only changes placement order**, not the objective: occluded labels are placed
  after visible ones but are still placed.
- **No GPU run in CI.** This project's harness forbids headless-browser automation, so the page
  itself is only checked with `python3 -m http.server` (`200` + importmap present) plus
  `node --check main.js`. The node path and the baked reference are what the numbers in this README
  come from; the in-page "vs node bake" line is what lets a human falsify the browser path in ten
  seconds.
